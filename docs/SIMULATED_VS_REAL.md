# What is simulated and what is real

A prototype like this is easy to oversell. This page states exactly which parts are synthetic and which parts are genuine working software.

## Simulated

| Thing | Detail |
| --- | --- |
| The facility | "Meridian Works Unit 3" does not exist. Its 32 assets, their positions, ratings and service dates are invented to be coherent, not copied from a real plant. |
| Every measurement | All 84 signals are generated by a process model in `src/simulation/SimulationEngine.ts`, with seeded random noise. No sensor, historian or control system is involved. |
| The physics | The process model is a deliberately small set of algebraic relations and first-order lags. It is causally coherent (a worn pump really does deliver less flow, which really does lower the reactor level) but it is not a validated engineering model and its numbers should not be used for design. |
| The faults | Three scenarios, injected as parameter changes. They are textbook failure progressions, compressed to about two minutes so they can be watched. |
| Operator actions | "Duty changeover" and "rate change" act on the simulated plant only. |
| The sonar | There is no physical scanner. The pulse is an interaction and inspection mechanism over data the system already holds. It does not sense anything. |
| Time | The plant clock starts at a fixed date and can run at up to eight times real time. |
| Alarm limits | Chosen to be plausible for the simulated equipment. |

## Real

| Thing | Detail |
| --- | --- |
| Normalisation | Tag resolution, unit conversion, rejection of bad readings: ordinary code operating on whatever it is given. |
| Anomaly detection | Six detectors computing means, z-scores, regression slopes and residual scatter on the incoming data. No anomaly is scripted; every one exists because a rule was satisfied by measurements, and the rule and numbers are recorded. The detection engine has no access to the scenario list. |
| Baseline learning | Baselines are learned from the data at start-up and re-learned after commanded changes. They are not hard-coded expected values. |
| The dependency graph | A real typed graph with real traversal. Its content describes a fictional plant; its mechanics are general. |
| Correlation | Incidents are assembled by graph distance and timing from whatever anomalies occur. Injecting two faults together produces two incidents because the algorithm separates them, not because a script says so. |
| Reasoning | Hypothesis scores are computed from which criteria are met by the anomalies actually present. Change the data and the ranking changes. |
| Impact projection | Computed by traversing the graph from the origin candidate. |
| Status numbers | Every figure in the top bar is derived from application state at that moment, including the frame rate and pipeline timing. |
| 3D interaction | Real-time WebGL rendering, ray-cast picking, camera control. |
| Agent workflow | Real orchestration code: context building, five agents with different inputs, parallel and sequential stages, timeouts, deadline, repair, cross-checks, audit trail. |
| Validation | The schema gate and grounding validator are real code that checks every cited ID against the investigation context. Their behaviour is tested and evaluated against 99 adversarial answers. |
| Claude integration | Real provider code on the official Anthropic SDK, with real request construction, error handling and key isolation. Tested against a local stub of the API; **not yet run against the live API** (see "AI" below). |

## Cyber layer: what is simulated and what is real

| Thing | Status |
| --- | --- |
| The OT network | **Simulated.** The zones, 14 devices, addresses (private ranges), vendor models, role accounts and change records are invented to fit the facility. No network is scanned, contacted or modelled from a real site. |
| Security telemetry | **Simulated.** Logons, flow summaries and controller audit entries come from `CyberSimulation`: background polling plus three scripted scenarios. There is no packet capture, no real authentication and no exploitation of anything. |
| The controller write | **Simulated.** One parameter, the cooling-tower fan speed setpoint, is wired into the process model. The UI and the engines have no path to write it; a test enforces this. |
| Cyber detection | **Real code.** Five rules evaluate whatever records arrive; they do not see the scenario list. |
| Cyber-physical assessment | **Real code.** It is deterministic, uses only declared relationships, and states its unknowns. |
| ATT&CK for ICS mappings | **Real reference data**, verified on attack.mitre.org (content v20.1). Shown as context, never as a finding. |

## AI: what exists and what has been verified

| Thing | Status |
| --- | --- |
| Claude provider and AI service | Implemented. Exercised against a local HTTP stub that imitates the Messages API. Never called against the real API, because no key was available while this was built. |
| Model output in screenshots | Produced by the **scripted test double**, which assembles answers mechanically from the context. It is not a language model, and every screen and report it produces carries a banner that says so. |
| Live-model results | None exist. `npm run eval:live` produces them when a key is configured. |

## How to check this yourself

- Run `npm test`. The end-to-end tests drive the pipeline headlessly and assert on its conclusions. One test replays recorded telemetry through a different adapter and gets the same incident and score, which could not happen if results were tied to the simulator.
- Open any anomaly in an investigation and compare the rule text with the trend chart beneath it.
- Trigger "Throughput change to 70 %". Flow drops by 30 % across the plant and nothing is flagged, because the change was commanded and baselines were re-learned.
- Lower sonar intensity below 0.6 while an advisory-level condition is active. The sweep report counts it as unheard instead of returning an echo.

## What this does not demonstrate

- **Performance on real plant data.** Real telemetry has gaps, drift, stuck sensors, mis-ranged transmitters and operating modes nobody documented. None of that is modelled here.
- **Diagnostic accuracy.** The reasoner ranks correctly on three scenarios designed alongside it, across 10 seeds (EVALUATION.md). That shows the mechanism works, not that it would be right on an unseen failure.
- **Scale.** Tested at 32 assets and 84 signals.
- **Language-model quality.** The detection, correlation and hypothesis scoring are deterministic rules, chosen so that every conclusion can be traced. The optional AI review has not been measured against a live model.

## Things this prototype deliberately does not do

It does not connect to, read from, or control any real machinery. It does not collect audio, track people, or access any device. It is a self-contained simulation and decision-support demonstration.
